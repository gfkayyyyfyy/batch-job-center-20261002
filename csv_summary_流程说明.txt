轻量批处理任务中心 内置数据汇总任务（csv_summary）流程说明
提交 → 手动执行 → 查询状态与结果（当前源码核对稿）
================================================================================

0. 范围、依据与核对结论
--------------------------------------------------------------------------------
0.1 本说明只覆盖一条路径：内置数据汇总任务 csv_summary 从公开命令行入口提交
    （submit）、手动执行（run）到查询记录（show）。不涉及新功能设计，不描述
    retry/cancel/请求键的完整语义（仅在与本路径入口相关处标注其存在）。

0.2 依据文件（均为当前工作区实际源码与现有文档，本次未做任何修改）：
    - task_center/__main__.py  命令行入口、参数解析、JSON 输出与退出码
    - task_center/core.py      SQLite 存储、提交、执行、查询全部核心逻辑
    - task_center/__init__.py  仅定义 __version__ = "0.1.0"
    - demo/sales.csv           现有演示输入（第 8 节示例不依赖该文件，
                               示例输入均由命令自行准备）
    - README.md                现有公开文档
    版本标识：task_center/__init__.py 的 __version__ = "0.1.0"；
    仓库当前提交为 bc31dd0。

0.3 核对结论：本路径在当前版本已闭环——
    登记（INSERT jobs 行，status=queued）→ 手动 run 同步执行并落库 →

    task_center/core.py: _run_csv_summary），不标注行号，以免版本演进后

1. 公开入口与通用输入输出形式
--------------------------------------------------------------------------------
1.1 唯一公开入口是命令行模块（task_center/__main__.py: build_parser、main）：

      python -m task_center [--db PATH] <submit|run|show|retry|cancel> ...

    本路径使用其中三个子命令：
      submit  登记任务（不执行）         参数：type 位置参数、--input（必填）、
                                          可选 --request-key（本路径不展开）
      run     手动执行一个 queued 任务   参数：id 位置参数
      show    查询已保存的任务记录       参数：id 位置参数
    （retry、cancel 子命令同样已实现并在 build_parser 中注册，但不属于
    submit→run→show 这条路径。）

1.2 --db 为全局参数，位于子命令之前；默认值 core.DEFAULT_DB =
    项目根目录/tasks.sqlite3（task_center/core.py: PROJECT_ROOT、DEFAULT_DB）。
    数据库不存在时由 core.connect 自动创建并建表，因此 show/run 也可指向
    一个全新库文件。

1.3 每次调用标准输出恰好打印一行 JSON，对象固定含四个键
    id、status、result、error（task_center/__main__.py: main 末尾的
    json.dumps(record, ensure_ascii=False)；记录构造见
    task_center/core.py: _record）。

1.4 退出码（task_center/__main__.py: main、_dispatch、_exit_code_on_success）：
    - 0：submit 成功；show 命中记录；retry/cancel 成功；
      run 仅在最终 status == "succeeded" 时为 0。
    - 1：业务拒绝或执行失败（core.TaskError 被捕获），JSON 的 error 填写
      错误码。
    - 2：argparse 参数层错误（如缺少 id、未知子命令），由 argparse 默认
      处理：stderr 打印 usage，不产出 JSON。此行为已实测。
    注：本机 shell 无 python 命令，实测使用 python3；以下示例以 README 的
    公开形式 python -m task_center 书写，本机执行时替换为 python3 即可。

2. 步骤一：提交（登记）——汇总输入取自哪里、是否登记入队
--------------------------------------------------------------------------------
2.1 入口形式
      python -m task_center [--db PATH] submit csv_summary --input <相对路径>
    对应 task_center/core.py: submit(conn, task_type, input_path,
    request_key=None)。

2.2 汇总输入的来源
    - 输入是一个 CSV 文件路径字符串，按原样存入 jobs.input（INSERT 绑定的
      是入参原字符串），后续执行时再按该字符串重新解析。
    - 路径解析规则见 task_center/core.py: _resolve_input：
      相对路径相对于“项目根目录”PROJECT_ROOT（即 task_center 包所在目录的
      上一级）拼接，而不是相对于当前 shell 工作目录；绝对路径直接使用。
      随后用 os.path.realpath 解析真实路径（符号链接会被展开），要求 demo
      目录的真实路径位于该文件真实路径的父级链中，且 real.is_file() 为真
      （普通文件、存在）。任一不满足即拒绝。
    - 提交阶段只做类型与路径/文件元数据检查，不打开、不读取文件内容
      （submit 全文无 open 调用；内容读取仅存在于 _run_csv_summary）。
      因此“提交时合法、执行时内容非法”的文件可以正常排队，第 8 节
      示例二正是这种情形（已实测）。

2.3 检查顺序与拒绝（task_center/core.py: submit）
    1) task_type 不在 TASK_TYPES（={"csv_summary"}）→
       抛 TaskError("invalid_type")。
    2) 若提供 --request-key：校验键并查同库绑定（本路径不使用该参数，
       细节从略；错误码 invalid_request_key / request_conflict 的入口与
       常量确实存在，见 _REQUEST_KEY_RE 及 submit 中的相应分支）。
    3) _resolve_input(input_path) 失败（文件不存在、在 demo/ 之外、
       不是普通文件、符号链接指向 demo/ 之外）→ TaskError("invalid_input")。
    拒绝时不写数据库（INSERT 在全部检查之后）。
    CLI 层输出固定为 {"id": null, "status": null, "result": null,
    "error": "<错误码>"}（submit 参数无 id，_rejection_record 回显 None，
    见 task_center/__main__.py: _rejection_record；invalid_type 与
    invalid_input 均已实测），退出码 1。

2.4 登记与“入队”的实际含义
    - 检查通过后：id = uuid.uuid4().hex（32 个十六进制字符，每次不同）；
      向 jobs 表 INSERT 一行：id、type、input、status="queued"、
      result=NULL、error=NULL、request_key（不带键时为 NULL），随后 commit。
    - 成功输出：{"id": <id>, "status": "queued", "result": null,
      "error": null}，退出码 0（已实测）。
    - “入队”在本版本中就是该 jobs 行的 status 取 queued：不存在独立的队列
      表，也没有任何后台进程或自动调度去取出任务。登记后任务保持 queued，
      直到被第 3 节的 run 显式执行。

2.5 存储结构（仅描述现状，不改变任何结构）
    task_center/core.py: connect 按 _SCHEMA 创建 jobs 表：
    id TEXT PRIMARY KEY, type TEXT, input TEXT, status TEXT,
    result TEXT, error TEXT；另有 request_key 列（旧库经
    _REQUEST_KEY_COLUMN 的 ALTER TABLE 补齐）与 request_key 唯一索引
    （_REQUEST_KEY_INDEX）。全库只有这一张业务表。

3. 步骤二：手动执行——什么操作开始执行、产出什么
--------------------------------------------------------------------------------
3.1 入口形式
      python -m task_center [--db PATH] run <id>
    CLI 经 task_center/__main__.py: _dispatch 调
    task_center/core.py: run(conn, job_id)。
    这是本版本中唯一会开始执行汇总的公开操作：同步在当前命令进程内完成，
    无线程、无子进程（core.py 未 import subprocess；README“计划采用
    subprocess”的设想在本路径上尚无对应实现）。

3.2 执行前置检查（task_center/core.py: run）
    1) _get_job 按 id 查行；查不到 → TaskError("job_not_found")。
    2) 该行 status 必须恰为 "queued"，否则 TaskError("invalid_state")，
       数据库不做任何改动。CLI 对 invalid_state 的响应由
       task_center/__main__.py: _rejection_record 附带该行当前保存的
       status 与 result、仅把响应中的 error 改为 "invalid_state"（退出码 1）；
       库里的 status、result、error 原值均不变（succeeded 行与 failed 行
       再 run 均已实测）。
    3) 再次调用 _resolve_input(input_path)——执行时重新解析路径并重新确认
       目标仍是 demo 目录内的普通文件。因此提交后文件被删除、移动或替换为
       指向 demo 外的链接，都会在执行期暴露。run 的 except 把提交期的同名
       错误码 invalid_input 改记为 input_error
       （code = ERR_INPUT if exc.code == ERR_INVALID_INPUT else exc.code）。
       提交后删除文件再 run 得到 failed/input_error，已实测。

3.3 汇总计算 task_center/core.py: _run_csv_summary(real_path)
    该函数以“直接迭代文件对象”的方式逐逻辑记录读取与累计，不一次性读取
    整份文件、不物化全部记录：
    - 打开：open(real_path, "r", encoding="utf-8", newline="")。
      * open 本身抛 OSError（如打开被系统拒绝）→ TaskError("input_error")
        （源码可证；本次核对在本机 DrvFs 文件系统上未能用权限位造出该
        条件，故不标实测）。
    - 解析与迭代：reader = csv.reader(fh)，循环中对 reader 调用 next() 逐行
      取得“一条逻辑记录”，每取得一条就立即校验并累计：
      * next() 抛 UnicodeDecodeError（字节不是合法 UTF-8）→
        TaskError("data_error")。逐行解码下，错误可能在已经读到若干合法
        记录之后才暴露（第二条数据处含坏字节的文件已实测为
        failed/data_error）。
      * next() 抛 csv.Error（数据被 CSV 解析器拒绝，如字段超过解析器默认
        长度上限）→ TaskError("data_error")，不向调用方或记录泄露底层
        异常文本（超长字段已实测）。
      * next() 抛 OSError（打开成功后迭代读取失败）→
        TaskError("input_error")（源码可证，本次未实测触发）。
    - 完全空行：物理行完全为空时 csv.reader 产出空列表 []，以 `if not row`
      一律忽略、不计入任何记录；表头之前出现的空行同样跳过，故第一条
      非空逻辑记录才被当作表头（含多条空行的文件已实测）。注意区分：
      只含空白字符（空格/制表符）的物理行会被解析为单元素列表而非空列表，
      不属于“完全空行”，将按普通记录参与表头或列数校验（纯空格行出现在
      表头位置已实测为 data_error）。
    - 引号内换行：一条逻辑记录的字段被双引号包围时，字段内部的换行属于
      该字段，csv.reader 会自行继续取下一物理行拼回同一条记录，不增加
      记录数、不计入 row_count（字段内含一个换行的两条数据已实测
      row_count=2，类别名中保留该换行）。字段内逗号同理不拆分为多列。
    - 表头：第一条非空逻辑记录的每个单元格去除首尾空格后，必须恰等于
      ["category", "amount"]，否则 data_error。
    - 数据行（表头之后的每条非空逻辑记录）：
      * 必须恰为两列，否则 data_error；
      * category = 第 1 列 strip，不能为空；代码未对类别做字符集限制，
        区分大小写（"A" 与 "a" 已实测为两个不同类别）；
      * amount = 第 2 列 strip，必须整串匹配正则 [0-9]+
        （_AMOUNT_RE.fullmatch），即非负整数字面量；否则 data_error
        （"x" 已实测）；
      * value = int(amount)，累计 row_count（数据逻辑记录计数，不含表头、
        不含空行）、total_amount（金额总和）、categories（按 strip 后的
        类别求和的 dict，键按首次出现顺序插入）。
    - 成功返回 dict：{"row_count", "total_amount", "categories"}。

3.4 两种“没有数据”的结局（按当前源码，二者不同）
    - 仅有表头（其后没有任何非空逻辑记录）：表头校验通过后循环正常结束，
      返回零汇总并成功落库：
      {"row_count": 0, "total_amount": 0, "categories": {}}，
      status=succeeded，退出码 0（已实测）。
    - 完全空文件，或内容仅由完全空行组成（header_seen 始终为假）：
      抛 TaskError("data_error")，run 落为 failed/data_error
      （空文件与仅含空行的文件均已实测）。

3.5 成功落库与输出（task_center/core.py: run）
    UPDATE 同一行：status="succeeded"，result=结果的 JSON 字符串
    （json.dumps(..., ensure_ascii=False)），error=NULL，commit。
    标准输出：{"id", "status": "succeeded", "result": {上述三个键},
    "error": null}，退出码 0（_exit_code_on_success 仅认 succeeded）。

3.6 失败落库与输出（task_center/core.py: run）
    执行期任何 TaskError 都走失败分支：UPDATE 同一行 status="failed"、
    result=NULL、error=错误码（input_error 或 data_error），commit；
    输出 {"id", "status": "failed", "result": null, "error": <错误码>}，
    退出码 1。失败不保留部分结果：即使此前已经读到并累计了合法行
    （如第二条数据才非法、或读到合法行后遇到坏 UTF-8 字节），result
    也直接置 NULL，库里不留任何中间汇总（已实测）。失败记录持久存在，
    可被 show 读回；对其再次 run 只会得到 3.2 的 invalid_state，保存值
    不变（已实测）。

3.7 文件关闭行为
    - open 成功后，读取、解析与累计整体位于 try 块中，finally 中无条件
      fh.close()：成功结束、解码失败、解析器拒绝、读取 OSError、表头或
      字段非法等所有退出路径都会关闭文件（见 _run_csv_summary 的
      try/finally）。
    - open 本身失败时不存在已打开的文件句柄，无需关闭；异常直接进入
      run 的失败落库分支。

3.8 内存特征（流式不等于恒定内存）
    当前实现不保留整份文件文本、也不把全部解析行物化为列表，但不能把
    流式读取解释为“恒定内存”。_run_csv_summary 的 docstring 自述为
    “工作内存只随类别数量、当前记录大小以及文件对象的读取缓冲增长”，
    具体地：
    - categories 随出现过的不同类别集合增长，row_count/total_amount
      本身为标量；正常情况下内存不随数据行总数线性增长；
    - csv.reader 必须在内存中持有“当前一条逻辑记录”——引号内换行的
      记录可能横跨多个物理行，单条记录或单个字段极大时这部分内存可能
      很大；
    - 文件对象自身维护读取缓冲。
    因此内存上限仍受类别数量与单条逻辑记录大小影响。

4. 步骤三：查询——实际能取得哪些状态和结果
--------------------------------------------------------------------------------
4.1 入口形式
      python -m task_center [--db PATH] show <id>
    对应 task_center/core.py: show → _get_job → _row_to_record。

4.2 show 只把数据库中该行当前内容原样读出：id、status，以及 result
    （非 NULL 时 json.loads 还原为对象，否则 null）、error 字符串。
    不执行任何计算、不触碰输入文件：对 failed/data_error 行反复 show
    不会重新解析 CSV、不会改变记录（已实测）。queued / succeeded /
    failed / cancelled 任一状态均可查询，命中即退出码 0。

4.3 id 不存在：_get_job 抛 job_not_found；CLI 输出
    {"id": "<你输入的 id>", "status": null, "result": null,
    "error": "job_not_found"}，退出码 1（已实测）。show 不会创建记录。

4.4 退出进程后记录仍可查询：数据保存在 --db 指定的 SQLite 文件中
    （默认项目根 tasks.sqlite3），换一次命令调用、换一个进程，只要指向同一
    数据库文件即可读回（已实测：run 之后再次 show 返回同一 succeeded 记录；
    failed 行的 show 记录与 run 失败响应逐字一致）。

5. 本路径的状态语义（仅列源码中存在的取值与流转）
--------------------------------------------------------------------------------
5.1 状态常量（task_center/core.py: STATUS_QUEUED/STATUS_SUCCEEDED/
    STATUS_FAILED/STATUS_CANCELLED）：queued / succeeded / failed /
    cancelled。
5.2 本路径实际发生的流转：
      submit 成功            → queued（新行）
      run 一个 queued 任务   → succeeded（结果落库）或 failed（错误码落库）
      show                   → 不改变状态
    run 对非 queued 行（succeeded/failed/cancelled）一律 invalid_state 且
    原记录不变（run 的状态检查在任何文件操作之前）。
5.3 另有两条已实现的公开流转不在本路径内，仅标注存在：
    retry 使 failed → queued（task_center/core.py: retry）、
    cancel 使 queued → cancelled（task_center/core.py: cancel）。
    被 cancel 的行不能再 run（同样落入 5.2 的 invalid_state）。

6. 总目标中提及、但当前源码在本路径上未实现的部分
--------------------------------------------------------------------------------
对照 README 开头（标题之后）的总目标逐项核对：
- 任务登记：已实现（本说明第 2 节）。
- 入队执行：仅实现“置为 queued + 手动 run 同步执行”；无自动执行、
  无后台队列消费者。自动/异步执行未实现。
- 状态查询：已实现（第 4 节）。
- 重试、取消：均已实现并有公开入口（retry/cancel），但不在本路径范围内。
- 结果留存：以 jobs 表同一行的 result/error/status 列持久保存；每次
  run/retry/cancel 都原地 UPDATE 覆盖旧值。不存在独立的多次执行历史/
  审计记录——若“执行记录”指每次执行留存一条历史，则该部分未实现。
- 依赖顺序：源码中无依赖字段、无依赖校验或排序逻辑，未实现。
- 简单定时计划：源码中无任何调度、定时器或时间字段，未实现。
- 网络 API、常驻服务：未实现；公开入口仅命令行一种形式。

8. 可核对的本地使用示例（共两个）
--------------------------------------------------------------------------------
约定：
- 在项目根目录（含 task_center/ 与 README.md 的目录）执行；示例输入均由
  下列 printf 命令自行写入 demo/ 目录，不假定仓库已存在 demo/sales.csv
  （demo/ 目录不存在时先执行 mkdir -p demo）。
- 两个示例各自使用独立的临时数据库（/tmp 下），不污染默认库。
- 命令采用 README 的公开形式 python -m task_center；本机无 python 命令，
  以下输出均为使用 python3 实测所得，执行时把 python 替换为 python3 即可。
- id 是 uuid4 的 32 位十六进制字符串，每次运行不同，属预期动态值。下文
  以 $ID / $BID 占位，代入方式二选一：
  方式 A（shell 自动捕获，实测可用）：
    ID=$(python3 -m task_center --db <库路径> submit csv_summary \
      --input <输入路径> | python3 -c 'import sys,json; print(json.load(sys.stdin)["id"])')
  方式 B：手工复制上一条 submit 输出 JSON 中的 id 字面值，把后续命令里的
    $ID/$BID 替换为该字符串。

示例一（正常路径：引号内逗号的类别，两条数据；下列命令与预期已实测）
---------------------------------------------------------------------
自备输入，文件内容共三行（表头 + 两条数据）：
    printf 'category,amount\n"a,b",10\n"a,b",5\n' > demo/_doc_example_success.csv

命令顺序、JSON 预期与退出码：
  python -m task_center --db /tmp/tc_doc_ok.sqlite3 submit csv_summary \
      --input demo/_doc_example_success.csv
  → {"id": "$ID", "status": "queued", "result": null, "error": null}      退出 0

  python -m task_center --db /tmp/tc_doc_ok.sqlite3 show $ID
  → {"id": "$ID", "status": "queued", "result": null, "error": null}      退出 0

  python -m task_center --db /tmp/tc_doc_ok.sqlite3 run $ID
  → {"id": "$ID", "status": "succeeded",
     "result": {"row_count": 2, "total_amount": 15,
                "categories": {"a,b": 15}},
     "error": null}                                                        退出 0

  python -m task_center --db /tmp/tc_doc_ok.sqlite3 show $ID
  → 与上面 run 的 succeeded 记录完全相同（换进程读回同一数据库）         退出 0

结果可由输入直接核对：两条数据记录（引号内的逗号是类别 "a,b" 的一部分，
不拆列）→ row_count=2；10+5=15 → total_amount=15；两条同属类别
"a,b" → categories={"a,b":15}。run 与 show 返回的是同一条已保存记录。
清理：
  rm -f demo/_doc_example_success.csv /tmp/tc_doc_ok.sqlite3

示例二（执行期数据非法 → failed/data_error；下列命令与预期已实测）
-------------------------------------------------------------------
自备输入：第一条数据合法、第二条金额非法（提交只查路径不读内容，故仍能
排队；run 时即使已读到合法行也不留部分汇总）：
    printf 'category,amount\na,10\nc,x\n' > demo/_doc_example_failure.csv

命令顺序、JSON 预期与退出码：
  python -m task_center --db /tmp/tc_doc_fail.sqlite3 submit csv_summary \
      --input demo/_doc_example_failure.csv
  → {"id": "$BID", "status": "queued", "result": null, "error": null}     退出 0

  python -m task_center --db /tmp/tc_doc_fail.sqlite3 run $BID
  → {"id": "$BID", "status": "failed", "result": null,
     "error": "data_error"}                                                退出 1
    （"x" 去空白后不匹配 [0-9]+；result 为 null，合法的 a,10 不形成
     部分汇总）

  python -m task_center --db /tmp/tc_doc_fail.sqlite3 show $BID
  → {"id": "$BID", "status": "failed", "result": null,
     "error": "data_error"}                                                退出 0
    （show 只原样读回保存记录，不重新解析文件、不重算；任意状态退出 0）

清理：
  rm -f demo/_doc_example_failure.csv /tmp/tc_doc_fail.sqlite3
